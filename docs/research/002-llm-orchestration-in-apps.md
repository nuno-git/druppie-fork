# LLM Orchestration within Built Apps — Platform Standard & Rationale

> Status: platform research, June 2026.
> Underpins two skills:
> - `druppie/skills/llm-orchestration-in-apps/SKILL.md` (architect — WHAT:
>   pattern, agency level, placement).
> - `druppie/skills/llm-orchestration-standard/SKILL.md` (builder_planner —
>   HOW: library, access pattern, code placement).
>
> This is not project-TD research. The goal is to establish **one standard**
> for how Druppie apps build in-app LLM logic — not to pick between twelve
> frameworks per project. The framework survey therefore sits at the back as
> supporting evidence (appendix), not as a selection menu.

## 1. Standard on one page

When an app generated by Druppie **itself** contains multi-step LLM logic
(not calling a Druppie agent, but running its own LLM steps), we build it
one way. Standardization beats per-project perfectionism: it keeps a growing
fleet of generated apps manageable, reviewable, and quick to understand.

| Agency decision (architect) | Standard implementation (builder_planner) | LLM access |
|---|---|---|
| **LLM + UI** (pattern #1–#2) | **Plain Python** — direct call + UI gate (Approve/Reject/edit). No framework. | `module-llm.chat` |
| **Sequential chain / evaluation loop** (#2–#3) | **Plain Python** — explicit functions/steps, `for` loop for evaluation. No framework. | `module-llm.chat` |
| **Single agent + tools** (#4) | **Plain Python, core style** — a small tool loop modeled on the platform agent loop: tool calls, a **mandatory `done` tool**, agents/tools in **YAML**, a max-iteration cap. No agent framework. | Direct provider SDK *(native tool-calling is required; module-llm.chat cannot do that yet — see §5)* |
| **Durable / multi-agent** (#5–#6) | **Escalation — not pre-baked.** Requires a deliberate platform decision before building; do not quietly pick a framework per project. | n/a |

**No agent framework.** Everything linear is plain Python; the single agent
with tools is a small core-style tool loop (see above). External agent
libraries (Pydantic-AI, LangGraph, CrewAI, …) carry real costs — version
churn, abstraction lock-in, harder debugging, a larger supply chain — and
are not the standard. Durable execution and true multi-agent are rare and
are standardized deliberately, not chosen ad hoc. A truly reusable core
runtime first requires making the platform loop app-usable (future work);
until then, "core style" is *modeled on* the core, hand-written per app.

**Default access pattern:** `module-llm.chat`, unless the pattern requires
something the module cannot do today (tool use, streaming, structured
output, multi-turn) — then direct SDK, with the reason stated in the plan.
That boundary moves as soon as module-llm v2 lands (§5).

## 2. Scope — Druppie agent vs in-app LLM workflow

| Aspect | Druppie agent | In-app LLM workflow |
|--------|---------------|---------------------|
| Who builds | Druppie platform team | Customer application |
| Code location | `druppie/agents/definitions/*.yaml` + Orchestrator | Inside the generated app |
| Runtime | Druppie Orchestrator + ToolExecutor | Own control flow |
| Governance | Approvals, HITL, role-based MCP permissions, audit | App handles its own logging/auth/errors |
| Tool access | MCP tools via tool_executor | Direct LLM call (module-llm or provider) |
| Activation | Planner schedules it | Endpoint or batch job in the app |
| Skill | `module-convention` | `llm-orchestration-in-apps` + `-standard` |

This standard applies **only** to the right-hand column. Building a new
Druppie platform agent falls outside it.

## 3. Conceptual framework — workflow patterns

The pattern — not the use-case domain — determines the structure.

| # | Pattern | Example | Characteristic |
|---|---------|-----------|----------------|
| 1 | **Single-shot** | "Summarize this ticket" | One prompt → one answer. No state, no ordering. |
| 2 | **Sequential chain** | draft → check → edit | Fixed order, linear, no branching. |
| 3 | **Evaluation loop** | nightly gold-set scoring | `for sample in dataset: call → judge → log`. Metric-driven. |
| 4 | **Single agent + tools** | "permit checker" with tools | One agent, multiple tools, ReAct loop. |
| 5 | **Stateful / durable** | multi-day approval flow, HITL pause | Persistent state, pause/resume, conditional branching. |
| 6 | **Multi-agent** | researcher + writer + reviewer | Multiple agents with roles, handoff or orchestrator-worker. |

> **2026 consensus** (Anthropic, Cognition, Shopify, MIT studies): pattern
> #4 is the surviving default multi-step pattern. In production, multi-agent
> (#6) is 58–285% more expensive in tokens than single-agent and degrades
> 2–15% on SWE-bench Verified when misapplied. **Default = #4, escalate to
> #6 only on measured capacity saturation.** This underpins why the standard
> stops at the single agent (#4) and treats multi-agent as a deliberate
> escalation.

## 4. The agency hierarchy (architect → WHAT)

The architect resolves the FD against a **strict ordering** and stops at the
first rule that fits. The outcome is a structural decision (no-agent /
single-agent / multi-agent), not a library.

1. **Simplicity first.** Design the simplest form that serves the FD. Extra
   agency is a cost (latency, tokens, failure modes, audit surface), not a
   feature.
2. **LLM + UI baseline.** One LLM call followed by a simple human action
   (Approve/Reject/edit) → **no agent.** Pattern #1–#2.
3. **Single agent.** Multiple distinct actions or tool use beyond
   generate-and-approve → **one agent with tools** (#4). Default ceiling for
   non-trivial in-app work.
4. **Multi-agent only on evidence.** Escalate to #6 only on measured
   single-agent saturation: information volume > one context window, or
   truly distinct, concurrent expertise domains. Name the evidence, or do
   not escalate.

## 5. The core question — extend module-llm or not? (v2 handoff)

Before any framework question stands a structural platform choice: **does
the LLM abstraction live in the modules or in the app?** Today `module-llm`
does one thing: `chat(prompt) → answer`. As a result, an in-app agent (#4)
currently has to use a direct provider SDK — bypassing the platform building
block, thus without the governance/consistency that `druppie.call("llm", …)`
provides.

### 5.1 Capability gap of `module-llm.chat` today

| Capability | `module-llm.chat` | Required for |
|------------|-------------------|--------------|
| Streaming (token stream) | ❌ | Agent UX, streaming responses |
| Tool use / function calling | ❌ | Every single-agent #4 (own core-style tool loop) |
| Structured output (JSON schema) | ❌ | Typed agent output, validation |
| Multi-turn message history | ❌ | All multi-step agent state |
| Vision (image inputs) | ❌ | Multimodal workflows |

### 5.2 Proposed direction (handoff — not in this PR)

Grow `module-llm` into a rich in-app LLM client so that generated apps stay
on the platform building block instead of each importing their own stack.
Concretely as v2 tools (analogous to the RAG Story-A/B split):

- `module-llm.chat_multi_turn` — multi-turn history + system/context.
- `module-llm.chat_with_tools` — function-calling/tool-use loop.
- (optional) structured-output mode + streaming events.

Effect: the single-agent standard (#4) can then run via `module-llm` instead
of direct SDK, and the access-pattern default shifts to "always module-llm".
**This is a platform roadmap item, not part of this skill PR.** The skills
are deliberately written as "module-llm unless it can't yet", so they shift
automatically once v2 lands.

> Open decision for the team: does this grow within `module-llm`, or does it
> become a broader `module-agents`? See the code-placement strategy in the
> `llm-orchestration-standard` skill (paths 3–4).

## 6. Recommendation (summary)

* **Default 2026:** Plain Python + `module-llm.chat` for #1–#3. Reach for a
  framework only when the pattern explicitly goes beyond linear *and* a
  direct SDK is acceptable.
* **One agent standard:** plain Python, core style for #4 — a small tool
  loop modeled on the platform agent loop (tool calls, mandatory `done`,
  YAML agents, max-iteration cap). No agent framework; not twelve options —
  one.
* **Multi-agent/durable defensively:** treat as an escalation that first
  needs a platform standard; do not build your own checkpointer or
  multi-agent framework per project.
* **No TR-LLM-XX dump** in TDs: the pattern + the structural decision belong
  in one compact subsection; the library belongs in the builder_plan.

### Why no archetype thinking (like RAG LS/HS/B)?

For RAG, LS/HS/B works because the quality archetype directly drives numeric
NFR targets. For LLM orchestration, the structural choice lies in the
**workflow pattern** (#1–#6), not in a quality archetype. The skills
therefore position patterns, not archetypes.

## Appendix A — Considered alternatives (supporting evidence)

> This survey underpins *why* the standard is plain Python (core style),
> *without* an agent framework. It is deliberately an appendix: a project
> architect or builder_planner does not need to work through it — the
> standard in §1 is the outcome.

### Cross-framework comparison

| Framework | Status (2026) | Sweet spot | `module-llm` fit | Verdict vs standard |
|-----------|---------------|-----------|------------------|--------------------------|
| **Plain Python (core style)** | stable | #1–#3 and the single agent #4 (own tool loop) | ✅ native (chat); direct SDK for native tool use | **Standard (baseline + agent)** |
| Pydantic-AI | V1 stable | typed single agent + tools | ❌ (direct SDK) | Not the standard — no framework |
| LangChain LCEL | 1.0 stable; legacy chains EOL Dec 2026 | linear pipelines | ✅ linear | Not needed alongside plain Python |
| LangGraph | 1.0 LTS | durable stateful, complex multi-agent | ❌ | Only on proven #5 escalation |
| DSPy | 3.x (alpha label) | metric-driven multi-stage | ✅ unique | Optional for #3 with a hard metric |
| LlamaIndex Workflows | 1.0 stable | event-driven multi-step | 🟡 partial | Only on #5 escalation |
| CrewAI | 1.x stable | role-based multi-agent | ❌ | Only on proven #6 (Python stack) |
| MAF | 1.0 GA Apr 2026 | multi-agent on Microsoft/.NET | ❌ | Only on proven #6 (MS stack) |
| Claude Agent SDK | 0.x (alpha) | app = autonomous Anthropic agent | ❌ | Anthropic-native only, vendor lock |
| AutoGen | **maintenance** | — | ❌ | Do not pick for greenfield |
| Semantic Kernel | succeeded by MAF | existing SK codebases | ❌ | Not for new work |
| Mirascope | 2.x, small community | anti-framework single calls | 🟡 | Plain Python is usually better |

### Why plain Python is the baseline
The 2026 industry consensus ("We ditched LangChain", roborhythms,
LangChain-1.0-upgrade lessons) is that ~80% of in-app LLM work is linear and
needs no framework; adding a framework "for later" is an anti-pattern. Plain
Python + `module-llm.chat` is therefore the baseline.

### Why no agent framework, but an own core-style loop
A single agent with tools (#4) needs a tool loop, but that is a small,
explicit loop — no reason to import an external agent library. The platform
already has the pattern in the core (`druppie/agents/loop.py`: tool calls,
mandatory `done`, YAML agents); apps model on that. One standard prevents
each app from choosing a different agent library, and avoids the costs of
frameworks (version churn, abstraction lock-in, harder debugging, supply
chain). Multi-agent (CrewAI/MAF) and durable engines (LangGraph) are
deliberately *not* pre-baked, in line with the 2026 consensus that premature
multi-agent is more expensive and worse.
